# Development history

This publication edition preserves the canonical BryceCast `master` line as a 301-commit history spanning **2026-06-08 through 2026-09-14**. Author names, author dates, and development order were retained during publication filtering. Commit messages preserve their narrative; embedded commit-ID references were rewritten to their filtered equivalents. Human author/committer emails on that filtered line use the owner's GitHub noreply identity; a handful of later launch-week commits carry the owner's ordinary Git email. Git object IDs changed because source-data and private-runtime paths were removed from every reachable tree.

The history is evidence of changes recorded in Git. It is not a transcript of prompts, chats, private messages, or every decision made during development. No conversation history was used to reconstruct this account.

## What the counts mean

- Canonical `master` contained **301 commits**. The publication line retains that 301-commit mainline shape after filtering.
- The original repository's 59 refs reached **305 distinct commits**. Canonical `master` reached 301 of them; four additional commits were reachable only from other refs and were not part of the maintained mainline. The public line should therefore be described as a preserved 301-commit canonical history, not as every object found in the private repository.
- The first original baseline commit, `Initial BryceCast baseline` on 2026-06-08, contained **1,633 tracked files**. That is the size of the original imported baseline tree, not the file count of the smaller publication tree.
- Git's author field records **293 commits under the name Jack Riddle** and **8 under the name Claude** on the canonical line. Those labels are preserved version-control metadata; they do not by themselves establish who designed a feature, which tools were used, or how work was divided.
- The private release workspace retains an old-to-new commit mapping for audit and support. That mapping is not part of the public repository because it would reconnect sanitized objects and paths to their private identities.

Because filtering rewrites each descendant of a changed tree, public commit SHAs cannot be compared directly with pre-publication SHAs. Refer to preserved dates, authors, subjects, and order when discussing lineage. Git history intentionally excludes raw timing captures, the career corpus, operational SQLite and runtime state. The career corpus and captures are published separately as a data release; see the [data release policy](../../DATA_RELEASE.md).

After the filtered line, the history continues with publication preparation and the September 2026 work that made this repository the single production codebase: the off-season site, the post-race automation rehearsal on the Mac mini, and the data release.

## Publication rewrite

The publication pass changed repository identity while preserving the useful development narrative. Filtering removed the raw and licensed corpus, live captures, private runtime and database artifacts, and their historical blobs. Any commit whose tree referenced those materials now has a different SHA, even when its subject, author, date, and source-code changes remain recognizable. Publication security checks inspect the working tree, reachable history, and the contents of each data release.

This distinction matters when validating a portfolio claim. Git can show when a decoder, contract, test, or generated report entered the codebase. It cannot make an unpublished input independently reproducible, turn a historical drill into current live proof, or establish a causal account of how the work was conceived. Use the [engineering atlas](../engineering/ENGINEERING_ATLAS.md) for capability and evidence locations, [development](../engineering/DEVELOPMENT.md) for runnable commands, and the [data release policy](../../DATA_RELEASE.md) for source and reproducibility boundaries.
